## 2026-10-12 — 객체 수명과 클래스 문법 기초

### 목표와 진행 상태

- 목표: 지역 객체의 생성자와 소멸자를 직접 작성하고 실행 순서를 관찰한다.
- 기초 실습 완료: 생성자 출력 뒤에 소멸자 출력이 각각 한 번 발생했다.
- Day 1 진행 중: Winsock 초기화 객체의 정상 경로를 구현하고 초기화·정리 반환값을 확인했다. 소켓 소유 객체, 이동 의미론, 루프백 서버는 아직 구현·검증하지 않았다.

### 실제 질문과 이해 과정

- RAII와 소켓 소유권을 이해하기 어려워하여, C의 명시적 자원 해제와 지역 객체의 수명을 연결해 설명했다.
- 소유자가 둘이면 데드락이 발생하는지 질문했다. 같은 소켓을 중복 정리하려는 이중 해제 문제와 데드락을 구분했다.
- closesocket을 호출하면 소멸자가 실행되는지 질문했다. 이번 설계의 호출 방향은 객체 수명 종료, 소멸자 실행, 소켓 정리 순서임을 설명했다.
- 객체 수명이 끝나는 시점을 사람이 판단하는지 질문했다. 지역 객체를 둘 범위는 개발자가 설계하고, 범위를 빠져나갈 때의 소멸자 호출은 C++ 규칙에 따른다고 설명했다.
- 함수에서 반환할 때 소멸자가 실행되고 그 안에 정리를 작성하는지 확인했다. 성공적으로 생성된 지역 관리 객체에 해당하며, 원시 SOCKET 변수나 new로 만든 객체와 구별해야 한다고 설명했다.
- INVALID_SOCKET이면 닫을 소켓이 없는지 확인했다. 현재 유효한 소켓을 소유하지 않는 상태로 설명했다.
- main.cpp 한 파일로 시작해도 되는지 질문했다. 초기에는 관리 클래스와 main을 한 파일에 두고 역할을 구분하도록 안내했다.
- C++ 문법을 전혀 모른다고 밝혔다. 클래스 정의, public 구역, 생성자, 소멸자를 작은 단계로 나누어 설명했다.
- 기초 실습 후 멘티는 지역 객체가 main의 반환 또는 함수 종료 때 수명을 마쳐 소멸자가 자동으로 호출된다고 설명했다. 이 실습의 지역 객체 수명에 관한 답변은 정확했다.

### 멘티가 직접 작성·수정한 내용

- src/main.cpp에 HelloWorld 클래스를 작성했다.
- 클래스 접근 지정자를 클래스 내부로 옮겼다.
- 클래스에 직접 둔 출력문을 생성자의 몸체 안으로 옮겼다.
- 주소를 보관하지 않는 new 표현식을 지역 객체 선언으로 바꿨다.
- 소멸자에 별도 출력 동작을 작성했다. main에는 소멸자를 직접 호출하는 문장이 없다.

### 설정 수정의 작성 주체

- 멘티가 CMakeLists.txt 수정을 명시적으로 요청했다.
- 멘토는 실행 대상 이름을 day01_raii, 소스 경로를 src/main.cpp로 맞췄다. Winsock 라이브러리 연결 대상과 일치시켰다.

- CMake 4.2.1 실행과 Visual Studio 2022 MSVC 19.43.34809 x64 컴파일러 실행을 확인했다.

- 실행한 구성 명령: cmake -S . -B build -G "Visual Studio 17 2022" -A x64

- 실행한 프로그램: build/Debug/day01_raii.exe
- 최종 실행에서 생성자의 인사 출력, 소멸자의 종료 인사 출력 순서를 확인했다. 각 출력은 한 번이었고 프로그램 종료 코드는 0이었다.

### 리뷰에서 발견한 점과 수정 결과

- Java 방식의 클래스 접근 지정자 위치가 C++ 클래스 선언에 맞지 않았다. 멘티가 public 구역을 클래스 중괄호 안으로 이동했다.
- 클래스 내부에 실행문을 직접 두었다. 멘티가 생성자를 작성해 출력문을 함수 몸체로 이동했다.
- new가 반환한 주소를 보관하지 않고 delete도 하지 않았다. 코드상 정리 책임이 남아 있음을 설명했고, 멘티가 지역 객체로 변경했다. 별도 메모리 누수 측정은 하지 않았다.
- 저장 위치 또는 저장 반영 문제로 초기 확인에서는 소스가 보이지 않거나 이전 내용이 읽혔다. 이후 지정된 경로의 수정된 파일을 확인했다.

### Winsock 초기화 객체 — 같은 날 이어서 진행

- 목표: 성공한 Winsock 초기화를 객체의 수명 종료 시 정리한다. 정상 실행 경로의 확인을 완료했다.
- 멘티는 초기화 성공 여부를 객체가 기억해야 한다고 답했다. 피드백에서는 객체마다 별도의 Winsock이 생기는 것이 아니라 성공한 WSAStartup 호출마다 WSACleanup 호출을 대응시키는 책임임을 설명했다.
- 멘티가 winsock2.h를 추가하고 WinsockRuntime 클래스를 직접 작성했다.
- 처음에는 flag를 생성자의 지역 변수로 선언하여 소멸자에서 접근할 수 없었다. 실제 빌드 오류를 확인한 뒤 멘티가 private 멤버 변수로 옮겼다.

- 멘티가 WSADATA 지역 변수, 버전 2.2를 표현하는 WORD 값, WSAStartup 호출을 작성했다.

- 출력문의 Std 대소문자 오타도 실제 컴파일 오류를 확인한 뒤 멘티가 수정했다.
- 멘티가 WSAStartup 반환값이 0일 때만 기존 flag를 true로 바꾸고, 소멸자에서 flag가 true일 때만 WSACleanup을 호출하도록 작성했다.
- 멘티가 기존 WSACleanup 호출의 반환값을 보관하고 출력했다. 초기화와 정리 출력에 구분 문구는 아직 없다.

- 실제 실행한 프로그램: build/Debug/day01_raii.exe. 생성자 인사, 초기화 반환값 0, 정리 반환값 0, 소멸자 인사 순으로 출력됐고 종료 코드는 0이었다.
- 현재 실행에서는 성공한 초기화와 정상적인 지역 객체 소멸에 따른 정리를 확인했다. 초기화 실패, 예외 경로, 복사에 따른 정리 책임 문제, 협상된 버전 검증은 아직 테스트하지 않았다. 복사 금지와 초기화 실패 시 이후 실행을 어떻게 막을지도 남아 있다.

## 2026-10-13 — 복사 금지 검증 및 세션 종료 인계

### 목표와 완료 여부
- WinsockRuntime의 복사 생성·복사 대입을 금지하고, 다음 예외 처리 학습으로 이어갈 상태를 저장한다.
- 복사 금지 선언과 멘티가 전달한 두 종류의 컴파일 오류를 확인했다.
- Day 1 진행 중이다. 날짜 변경을 Day 2 진입으로 취급하지 않는다.

### 질문, 답변, 피드백
- 초기화 실패 반환값을 INVALID_SOCKET으로 생각했다. WSAStartup의 int 오류 코드와 socket의 무효 핸들 값을 구별하도록 설명했다.
- 복사를 금지해야 한다고 답했다. 성공한 초기화 호출을 추가하지 않는 복사 때문에 flag만 복제되어 정리 책임이 중복되는 것이 핵심임을 설명했다.
- 복사 생성은 새 객체 만들기, 복사 대입은 기존 객체에 대입하기라는 구분을 확인했다.
- C에서 주소를 전달할 때 사용하던 &를 알고 있다고 말했다. C++ 선언의 참조는 같은 객체의 다른 이름이라고 설명했다.
- 참조를 통해 수정하면 복사본만 바뀔 것이라고 답했다. 참조에는 별도 복사본이 생기지 않아 원본이 바뀐다는 점을 교정했고 const 참조를 설명했다.
- 생성자가 예외를 던질 때 소멸자가 호출되지 않으므로 WSAStartup 자체의 실패에도 정리가 필요하다고 생각했다. 실패 전에 성공한 획득이 있었는지가 기준이며, API 자체 실패에는 cleanup이 필요 없다고 설명했다.
- 초기화 성공 후 버전 검사 실패에도 정리가 필요 없을 것 같다고 답했다. 성공한 초기화는 존재하고 해당 객체의 소멸자는 호출되지 않으므로 예외 전 직접 정리가 필요하다고 설명했다. 이후 독립적인 재설명은 아직 받지 않았다.

### 멘티의 구현과 리뷰
- 복사 생성자를 const 참조를 받는 삭제된 함수로 작성했다.
- 복사 대입을 처음 추가할 때 복사 생성자 선언을 지웠고 반환형의 참조 표시도 빠졌다. 두 선언을 함께 유지하고 자기 타입 참조 반환형으로 수정했다.
- 마지막 실제 파일 확인에서 두 금지 선언이 모두 있고 임시 복사 검증 문장과 추가 객체는 제거되어 있었다.
- C++ 소스는 멘티가 작성·수정했다. 이번 저장 작업에서는 소스와 CMake 내용을 그대로 보존한다.
